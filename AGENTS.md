## Readability and complexity

- Readability comes first. A person or an agent should be able to read a component top to bottom in its own file and understand it. When readability conflicts with shorter code, fewer files or less duplication, choose readability
- Keep complexity low: plain signals, inputs, outputs and services. No generic base classes, controllers, or components configured by large option objects
- Extract shared code only when there are three or more copies and the shared part has a clear name of its own (`RowActions`, `CheckboxGroup`). Similar-looking code that reads clearly where it is stays where it is; for example, each list card keeps its own create, delete and reload logic
- Keep each file about one thing. When a component mixes concerns (layout and data formatting, say), move the pure logic to `utils/` with a spec
- Name things for what they do, and write comments that explain why rather than what

## Components

- A component's public members are its inputs and outputs. Everything its template uses is `protected`, and everything else `private`, so the class shows at a glance what a parent can bind to. Specs drive components through the DOM rather than their internals

## Forms

- Every form uses Signal Forms: `form(model, schema, { submission: { action: async () => this.save() } })` bound with `<form [formRoot]>` and `[formField]`. The action delegates to a private method that runs the request through a `requestStatus`
- An edit form takes its model from `linkedSignal(() => ({ ... this.item() }))`, so it follows the edited record without an `effect`
- Put cross-field rules on the field that shows the error (`validate(path.confirmPassword, ...)`), so `<mat-error>` shows it without an `ErrorStateMatcher`

## Angular Material

- The single M3 theme lives in `src/styles.scss` (`mat.$cyan-palette` primary, `mat.$orange-palette` tertiary, Roboto, density 0). `color-scheme` is set on `html`; `ThemeService` switches it between `light`, `dark`, and `light dark`
- Use `--app-success` (defined in `src/styles.scss`) for success states; M3 has no success role
- Shared building blocks: section cards (`.section-card`, `.card-header-container`, `.card-content`), forms (`.form-stack`, `.compact-form`) are global classes documented in `src/styles.scss`; tables, edit panels, row buttons, checkbox lists and request feedback are components in `src/app/components/` (`FilteredTable`, `EditPanel`, `RowActions`, `CheckboxGroup`, `RequestFeedback`, with `requestStatus` and `resourceDataSource` in `utils/`). Use them instead of restyling or rewiring the same thing in a component
- Import table directives through `MAT_TABLE` from `src/app/utils/material-table.ts`

## API clients

- Two clients are generated by `make codegen`: `services/admin` (from `openapi/admin.yaml`) and `services/auth-basic` (from `openapi/auth_basic.yaml`)
- The specs in `openapi/` are vendored from Kerberos; keep them byte-identical with upstream
- Both clients export classes with the same names (`UsersService`, `User`, `Group`), so always import from the client's directory, never a barrel that merges them

## Verification

- Format: `make format` (CI runs `make format/check`)
- Build: `make build/prod`
- Lint: `make lint` (CI runs `make lint/ci`)
- Test: `make test`
- `make check` runs the CI sequence in one go
- Every page spec must call `expectNoAxeViolations` from `src/testing/axe.ts`
